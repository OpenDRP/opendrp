# Audit findings

The register for [plan 009](exec-plans/009-staged-audit.md). One row per finding,
append-only, with the evidence that makes it checkable and the disposition that
closes it. The register is the audit's memory: a step reads it before it starts and
after it stops, and a finding that is not here did not survive triage.

The register starts empty on purpose. Filling it ahead of the work would be a list
of suspicions, and the rule below is that a suspicion is not a finding.

## Severity

| Level | Meaning | Examples | Response |
|---|---|---|---|
| **S1** | Exploitable, or loses data | cross-tenant read, auth bypass, a finding silently dropped, provider key in a log, an audit row that can be forged | fix in the step with a regression test, or stop the audit and raise it |
| **S2** | Breaks a documented guarantee | audit gap on a state change, duplicate alert, wrong severity on a page, quota overrun, contract the SPA relies on | fix in the step if small, otherwise a plan with a date |
| **S3** | A defect with a workaround | wrong count, stale cache, race that needs a retry, confusing error on a rare path | register, then batch by area |
| **S4** | Clarity and maintenance | duplicated rule, dead branch, misleading name, missing comment where the invariant lives | collect for one cleanup pass; never spend an S1 budget here |

Severity is about blast radius, not about how hard the code is to read. A one-line
bug that shows one tenant another tenant's asset is S1; a 200-line module that is
merely convoluted is S4.

## Disposition

| Disposition | Means | Requires |
|---|---|---|
| `fixed` | the change is in this step | a regression test that fails before it, and a green suite after |
| `planned` | a later plan carries it | the plan's name in the row |
| `accepted` | the trade-off stays | a sentence in [security.md](security.md#accepted-risks-and-what-bounds-each-one) or in [the readiness page](production-readiness.md) that an operator can read |
| `duplicate` | repeats another row | the ID it repeats |

A step may not end with a finding whose disposition is empty. `open` is a
transitional value that exists only inside a step.

## A finding is filed only with

1. **Where** — `file:line` and the path that reaches it, not the whole call graph.
2. **Reproduction** — a failing test, a command with its output, or a request and
   response pair. Small enough to paste into the row's Evidence cell or into a
   linked test name.
3. **Impact** — who is affected and what they lose, in the operator's terms.
4. **Fix size** — `S` (≤ 20 lines), `M` (≤ 150), `L` (its own plan), so the next
   step can budget without reading the code again.

Without (2) the row is an open thread and belongs in the step's handoff, not here.

## Closing a wave

At the end of each wave (see the plan's Progress table) the register is re-read as a
whole, because a later step's finding often halves an earlier one's severity:

- two rows with the same root cause become one row with two symptoms;
- a row whose fix is now obvious and small is promoted into the next step;
- an `accepted` row that nobody can state in one sentence for an operator is not a
  decision — it goes back to `open` and into the next step's `Ask`.

The wave is over only when every row is `fixed`, `planned`, `accepted` or
`duplicate`, and the plan's handoff names the rows the next wave should expect.

Risk divided by cost, with the register's size column as the cost. No row needs a

1. **Pass A — evidence that is lost or misattributed** (AUD-015, 016, 018, 019, 026, 030, 032, 088;

3. **Pass C — debt with a workaround** (AUD-022, 033, 057, 060, 089; all `S`). Each has

All three passes are closed (2026-10-22, nineteen rows), the last of them on the day

the severity first, then the size: an `S2` that takes a morning goes before an `S3`
that takes a day, and nothing in pass C was allowed to displace anything in pass A.
